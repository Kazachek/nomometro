# Nomometro — покроковий план розробки

Навчальний проєкт: мінімалістичний веб-метроном. Стек: чистий HTML/CSS/JS (без фреймворків), Web Audio API для точного таймінгу, localStorage для збереження налаштувань. Робота — через git/GitHub. Дизайн (десктоп + мобільний) уже готовий, звіряння з макетом — на твоїй стороні.

**Як користуватись цим планом:** проходиш крок, показуєш результат, консультуємось, рухаємось далі. План — не догма, адаптуємо по ходу.

---

## Фаза 0. Фундамент і git

Мета: підготувати робоче середовище і навчитись базовому git-флоу.

- Створити папку проєкту, базову структуру файлів: `index.html`, `style.css`, `script.js`.
- Ініціалізувати git-репозиторій локально (`git init`), створити репозиторій на GitHub, підключити (`git remote add`).
- Навчитись базовому циклу: `git add` → `git commit` → `git push`. Зробити перший коміт із порожнім скелетом.
- Домовитись про просту угоду про коміти (наприклад, короткий опис українською/англійською — не критично, аби було зрозуміло).

Чекпоїнт: репозиторій на GitHub існує, у ньому є перший коміт із трьома порожніми файлами.

## Фаза 1. Статичний каркас (HTML + CSS)

Мета: зверстати інтерфейс без жодної логіки — просто "картинка", що повторює макет.

- Розмітити HTML-структуру: блок з BPM, кнопки +/- або слайдер, вибір розміру такту, кнопка Play/Pause, візуальний індикатор такту.
- Стилізувати під десктопну версію макета.
- Додати медіа-запити / адаптивну верстку під мобільний макет.
- Жодних `<script>`-дій ще немає — усе статично.

Чекпоїнт: сторінка виглядає як макет на десктопі й на телефоні (можна перевірити через DevTools → responsive mode).

## Фаза 2. Базова інтерактивність (JS без звуку)

Мета: навчитись основ JS — вибір елементів, події, стан застосунку — ще без аудіо.

- Обрати елементи через `document.querySelector`.
- Навісити обробники подій на кнопки (`addEventListener`).
- Завести один простий JS-об'єкт `state` (наприклад `{ bpm: 120, beatsPerMeasure: 4 }`), який зберігає поточні налаштування.
- Реалізувати зміну BPM і розміру такту через UI, з оновленням тексту/вигляду на сторінці при зміні `state` (це вручну — концепція "стан → оновлення DOM", яку пізніше роблять фреймворки за тебе).

Чекпоїнт: можна змінювати BPM і розмір такту кнопками, цифри на екрані оновлюються. Звуку і кліків ще немає.

## Фаза 3. Наївний метроном (навчальна вправа з дефектом)

Мета: свідомо зробити "неправильну" версію на `setInterval`, щоб на власні очі побачити проблему дрейфу — це важлива навчальна ланка перед Фазою 5.

- Play/Pause запускає/зупиняє `setInterval`, який раз на `60000/bpm` мс програє звук (можна навіть просто `console.log` або блимання елемента, поки нема аудіо).
- Помітити на практиці: якщо змінити вкладку в браузері на хвилину і повернутись — ритм "поїде". Це і є дрейф, про який говорили раніше.

Чекпоїнт: працює простий play/pause-цикл, і ти на власному досвіді бачиш, чому цього недостатньо для нормального метронома.

## Фаза 4. Знайомство з Web Audio API

Мета: навчитись базово працювати з `AudioContext` окремо від логіки метронома.

- Створити `AudioContext`.
- Завантажити готовий звуковий семпл (клік) і навчитись його програвати one-shot по кліку кнопки.
- Розібратись, що таке `AudioContext.currentTime` і чому це надійніший "годинник", ніж звичайний JS-таймер.
- Важливий мобільний нюанс: браузери (особливо Safari) блокують автозапуск звуку без взаємодії користувача — `AudioContext` треба "розблокувати" першим кліком/тапом. Це варто перевірити одразу на телефоні.

Чекпоїнт: клік по кнопці програє звук через Web Audio API (ще без циклу/темпу).

---

## Фаза 5. Точний таймінг (lookahead scheduling)

Мета: замінити наївний `setInterval` на правильну схему планування звуків наперед.

- Реалізувати алгоритм: невеликий `setInterval` (умовно раз на 25 мс) не грає звук напряму, а перевіряє — чи не час запланувати наступні кліки в межах "вікна наперед" (lookahead), використовуючи `AudioContext.currentTime` як опору.
- Додати акцент на перший удар такту (інший звук/гучність).
- Синхронізувати візуальний індикатор такту з реальними запланованими кліками (це окремий нюанс — візуал і аудіо тут не одне й те саме "джерело правди").
- Реалізувати tap-tempo (визначення BPM за ритмом натискань).

Чекпоїнт: метроном тримає темп стабільно навіть при згорнутій/неактивній вкладці, звучить акцент на перший такт, tap-tempo працює.

## Фаза 6. Збереження налаштувань (localStorage)

Мета: щоб BPM, розмір такту й інші налаштування не губились між сесіями.

- Зберігати `state` у `localStorage` при кожній зміні (або на паузу/вихід).
- При завантаженні сторінки — підвантажувати збережені значення, з розумними значеннями за замовчуванням, якщо збереженого нема.

Чекпоїнт: після зміни BPM і перезавантаження сторінки (навіть за два дні) — значення на місці.

---

## Фаза 7. Адаптивність і мобільна перевірка

Мета: переконатись, що все ще й реально зручно користуватись на телефоні, не лише "виглядає".

- Перевірити touch-взаємодію (розмір кнопок, зони натискання).
- Перевірити роботу на реальному мобільному браузері (не лише DevTools-емуляція), особливо розблокування звуку.
- Підправити верстку під проміжні розміри екранів за потреби.

Чекпоїнт: застосунком зручно і коректно користуватись з телефону вживу.

## Фаза 8. Мікроінтеракції та анімації

Мета: додати той шар "приємності", який відрізняє готовий продукт від навчального прототипу.

- Анімація індикатора такту в такт клікам.
- Плавні переходи/фідбек на кнопках (натискання, ховер, активний стан).
- Дрібні деталі за макетом, які раніше відклали.

Чекпоїнт: застосунок відчувається "живим", а не статичним.

---

## Фаза 9. Тестування та крайні випадки

Мета: перевірити, що застосунок не ламається в нетипових ситуаціях.

- Дуже низький/високий BPM (межі діапазону).
- Поведінка при згортанні вкладки/переключенні застосунків.
- Повторний play/pause без зависань чи накладання звуків.
- Базова доступність: чи можна керувати з клавіатури, чи є зрозумілі підписи для елементів керування.

Чекпоїнт: немає очевидних багів при звичайному й "недбалому" використанні.
